# Paper C measurement specification C2 (additional measures)

Status: written 2026-11-06 after C1 started and before any C1 result was read. Its parts B and C are frozen only after
their smoke runs pass; part A is frozen now. Hash in `paper_c/prereg/MANIFEST`. Pre-specified, not publicly registered.

## Part A. Evaluation gap (analysis of C1 traces, no new runs)
For each cell, over the overwrites with known old bytes:
measured delta ratio D = sum of zlib-1 size of (old XOR new) / (n x 4096);
compression ratio C = sum of zlib-1 size of the new page / (n x 4096);
best ratio B = sum of min(delta size, new size, 4096) / (n x 4096).
Reported against the assumed means Rc = 0.20, 0.35, 0.50 of Delta-FTL (Wu and He, EuroSys 2012) as D / Rc.
This estimates stored bytes only. It is not a replication of Delta-FTL: it has no delta log, garbage collection, buffer
or selective use of deltas, and it must be described so. Also reported per class group, so that the classes where deltas
help and where they do not are visible. Code: `exp/analyze_c.py`.

## Part B. Churned file-system state
- New state SG-T0: source tree, then 5 rounds of copying randomly chosen files of `/usr` until 70 % of capacity is used
  and deleting randomly chosen aged files down to 45 %, seed = replicate number, no TRIM (`exp2/churn_age.py`).
- The block map is taken after aging. Pages written earlier that belong to no live file form the `churned` class, by
  elimination; the F2FS rule for whole segments of C1 applies first.
- File systems: ext4, XFS, Btrfs, F2FS. Tools: targz, rsync, sqlite. 5 replicates. 60 runs.
- Compared with SC-T0 of C1 descriptively, per file system and tool, by overwrite share, class shares and delta ratio.
- `churned` may mix freed data with freed metadata, and this must be stated.

## Part C. Block-layer cross-check without the emulated SSD
- Same guest image and kernel. Data device: a 7168-MiB loop file in the guest, through dm-log-writes; the FEMU SSD holds
  no data and no FTL trace is taken. The log becomes the same record format (`exp2/logw_to_trace.py`), so the analysis is
  the same. Old and new bytes come from replaying the log.
- Same preparation, map and tool as C1. Conditions SC-T0 and SC-TF. File systems: ext4, XFS, Btrfs, F2FS. Tools: targz,
  rsync, sqlite. 3 replicates. 72 runs.
- What it can show: whether file-system-level results depend on the emulated SSD. What it cannot show: FTL behaviour,
  or how a real SSD behaves. A loop file differs from an NVMe device in reported limits and discard handling.
- Compared with the same C1 cells. A difference above 5 percentage points in the mean overwrite share, or above 0.05 in
  the mean delta ratio, is reported as a disagreement and examined; it is not removed.

## Rules for B and C
Failed runs are rerun once and reported. Smoke runs, one per file system, are not manuscript data. If a smoke run shows a
design fault, the fix and the reason are recorded here before the campaign starts. C1 is not changed by anything here.
