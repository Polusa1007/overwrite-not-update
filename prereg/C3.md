# Paper C measurement specification C3 (device size)

Status: written 2026-11-10 after C1 and C2 results were read; frozen 2026-11-10 after its 4 smoke runs passed
(device 14336 MiB confirmed by `df`, unmapped pre-tool pages at most 0.14 %, `retained_now` 0, no design fault), before
any formal run. Hashes in `paper_c/prereg/MANIFEST`. Two emulators of this size do not fit in the VM's 31 GiB, so one
instance runs (as allowed below). Pre-specified, not publicly
registered. Because it was written after the C1 and C2 results were known, the manuscript must say so.

## Question
Do the C1 results on overwrite share, classes and delta ratio depend on the 7168-MiB device size?

## Design
- Same guest image, kernel, trace mode, block map, tools and analysis as C1 (`exp/femu_fs.sh`, `exp/fs_map.py`,
  `exp/analyze_c.py`); only the FEMU device size changes, to 14336 MiB.
- Same absolute preparation as C1: S0-T0 (source tree only), SC-T0 (two deleted copies of `/usr`, no TRIM),
  SC-TF (two deleted copies, `fstrim` after the deletion). The deleted data are thus a smaller fraction of the device.
- File systems: ext4, XFS, Btrfs, F2FS. Tools: targz, rsync, sqlite. 3 replicates. 4 x 3 x 3 x 3 = 108 runs, in a fixed
  random order (seed 20261110).

## Comparison
Descriptive, per file system, tool and condition, against the same C1 cells: mean overwrite share, class shares of
overwrites and mean delta ratio. A difference above 5 percentage points in the mean overwrite share, or above 0.05 in
the mean delta ratio, is reported as a size effect and is not removed. No other comparison is made.

## Validity
C1 gates G1, G2 and G4 apply unchanged. If the VM cannot hold two 14336-MiB emulators, the runs use one instance; this
changes only the duration.

## Smoke runs
One per file system (SC-TF, targz, replicate 0), not manuscript data. A design fault found there is fixed and recorded
here before the formal runs.

## Limits to state
Two device sizes only; same absolute amount of stale data, so size and stale fraction change together.
