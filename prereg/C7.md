# Paper C measurement specification C7 (workloads that update existing data)

Status: written 2026-11-12 after the C1 to C5 results were read and after a reviewer noted that the C1 tools, except
sqlite, only create files, so that no overwrite can replace data that existed before the tool. Frozen 2026-11-13 after
its 4 smoke runs passed (data created, 44-79 MiB; mapped as live; tools completed without error; unmapped pre-tool
pages at most 0.14 %; analyze_c.py reads the traces), before any formal run. The smoke runs showed that the C1 rule
(only the first overwrite of a page gets the class of its earlier contents) counts most updates of live pages as tool
rewrites; the second main measure below was added for this reason before the freeze. Hashes in `paper_c/prereg/MANIFEST`. Pre-specified, not publicly registered.
Because it was written after the earlier results were known, the manuscript must say so.

## Question
When a tool updates data that already existed before it ran, what share of its overwrites replaces those data, and how
similar are old and new contents, on the four file systems, without and with deleted data and TRIM?

## Workloads (`exp7/c7_wl.py`)
Both create their data in `/mnt/live` right after the source tree, before any block map, so that these blocks are
mapped as class `live` (`exp7/fs_map_c7.py`); the tool then updates them. Both are our own scripts, not standard
benchmarks; fixed seeds as in the C1 sqlite tool, so replicates differ by timing only.
- dbupd: an SQLite database of 200000 rows (row generator of the C1 sqlite tool) is created during preparation; the
  tool runs 400 transactions of 250 updates of random existing rows (default rollback journal). Unlike the C1 sqlite
  tool, which creates its database during the tool, the updated rows exist before the tool.
- logapp: 2000 text files of 8-32 KiB are created during preparation; the tool appends 0.5-8 KiB of text to a random
  existing file 20000 times, each append followed by `fsync` (as in mail-server or log workloads).

## Design
- Released trace build, guest image (overlays, instances 3 and 4), kernel 6.8.0-147, 7168-MiB geometry and
  `exp/analyze_c.py` as in C4. Unlike C1 to C5 and all but six C6 runs, the guests' automatic package upgrades are switched off
  (apt-daily timers and unattended-upgrades masked; see the C6 note of 2026-11-12 in `prereg/MANIFEST`), so that the
  guest kernel cannot change during the campaign. Run script `exp7/femu_fs_c7.sh` and block map `exp7/fs_map_c7.py`, generated from `exp/femu_fs.sh` and
  `exp/fs_map.py` by `exp7/make_c7_scripts.py`; the only changes are the two tools, the preparation step and the
  mapping of `/mnt/live`. Batch runner `exp7/c7_batch.sh`, launcher `exp7/c7_run.sh`.
- Conditions S0-T0, SC-T0, SC-TF (as in C1); file systems ext4, XFS, Btrfs, F2FS; tools dbupd, logapp; 3 replicates:
  72 runs in a fixed random order (seed 20261114).

## Measures and reporting
Per cell, as in C1: overwrite share; share of overwrites per class (live, freed, source, metadata, F2FS dead log,
tool rewrite, unclassified); delta ratio and compression ratio per class; per-run minimum and maximum overwrite share.
Second, by `exp7/c7_pages.py`: every overwrite, first or later, classed by what its page held before the tool, with
delta ratio, compression ratio (new page, at most 4096 bytes) and the gain of also allowing the delta. Main statement:
for each cell, the share of overwrites of pages that held live data before the tool, and their delta ratio against the
compression ratio of the new pages. All 24 cells are reported whatever the result. No margins and no hypothesis test;
the results are descriptive. They are not pooled with C1.

## Validity
C1 gates G1 (unmapped pre-tool pages at most 5 %) and G4 (failed runs rerun once, tool errors reported) apply. G2 is
not informative (released build). The preparation must create the data (`prep_live.txt`); a run whose preparation
fails is a failed run.

## Smoke runs
Four runs, replicate 0 (ext4 SC-T0 dbupd, XFS SC-T0 logapp, Btrfs SC-TF dbupd, F2FS S0-T0 logapp), not manuscript
data: the data are created and mapped as live, the tool completes, `analyze_c.py` reads the traces. A design fault found
there is fixed and recorded here before the formal runs.

## Limits to state
Two synthetic workloads of our own, fixed seeds, three replicates, three conditions, one device size; written after
the earlier results were known.
