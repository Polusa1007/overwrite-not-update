# Paper C measurement specification C5 (deleted-data fraction)

Status: written 2026-11-11 after the C1 to C4 results were read; frozen 2026-11-11 after its 4 smoke runs passed (four
copies fit on every file system, 60-66 % of the device used after copying; 14336-MiB geometry, 4194304 pages as in C3;
unmapped pre-tool pages at most 0.14 %; no tool error; no design fault), before any formal run. Hashes in
`paper_c/prereg/MANIFEST`. Pre-specified, not publicly
registered. Because it was written after the C1 to C4 results were known, the manuscript must say so.

## Question
C3 doubled the device (7168 to 14336 MiB) but kept the same two deleted copies, so the capacity and the fraction of the
device holding deleted data changed together. Do the C1 and C3 results under untrimmed deleted data follow the
capacity or the deleted-data fraction?

## Design
- Device 14336 MiB (C3 geometry: `blks_per_pl=2048`, `ssd_size=14336`).
- New state SD-T0: four copies of `/usr` written and deleted without TRIM (C1's SC-T0 does the same with two). Four
  copies on 14336 MiB give about the deleted-data fraction of two copies on 7168 MiB. The source tree, and hence the
  fraction of live data, is the same in absolute size, so the live fraction and the total fill are lower than in C1.
- Script: `exp5/femu_fs_c5.sh`, generated from `exp/femu_fs.sh` by `exp5/make_c5_scripts.py`; the only changes are the
  SD case and the removal of the fourth copy. Batch runner `exp5/c5_batch.sh` (from `exp3/c3_batch.sh`, calls the C5
  script). Block map, guest image (copy-on-write overlay), kernel and `exp/analyze_c.py` as in C1.
- Build: the released trace build of C4 (stock FEMU 2d50161f + `femu/apply_trace.py`).
- File systems ext4, XFS, Btrfs, F2FS; tools targz, rsync, sqlite; 3 replicates: 36 runs in a fixed random order (seed
  20261112), one emulator instance (two of this size do not fit in the VM's memory).

## Comparisons
Margins as in C2 to C4: a difference of more than 5 percentage points in the mean overwrite share or more than 0.05 in
the mean delta ratio. Per file system and tool (12 cells):
1. Same deleted fraction, different capacity: C5 SD-T0 (14336 MiB, four copies) against C1 SC-T0 (7168 MiB, two).
2. Same capacity, different deleted fraction: C5 SD-T0 against C3 SC-T0 (14336 MiB, two copies).
3. Same deleted fraction, different capacity, existing data only: C3 SC-T0 (14336 MiB, two copies) against C1 SB-T0
   (7168 MiB, one copy). Both data sets were read before this specification was written.
Also reported per cell: mean share of overwrites landing on freed blocks, per-run minimum and maximum overwrite share.
How a result is described: if comparison 1 agrees in a cell where C3 showed a size effect, the C3 effect is described
as consistent with the change in deleted-data fraction rather than in capacity; it is not attributed to the fraction
alone, because the live fraction and the total fill also differ. No other comparison is made. All 12 cells of each
comparison are reported whatever the result.

## Validity
C1 gates G1 (unmapped pre-tool pages at most 5 %) and G4 (failed runs rerun once, tool errors reported) apply. G2 is not
informative with the released build (no retention by construction). The four copies must fit: a run whose preparation
fails is a failed run.

## Smoke runs
One per file system (SD-T0, targz, replicate 0), not manuscript data, to check that four copies fit on each file
system (`prep.txt`), that the device is 14336 MiB and that `analyze_c.py` reads the traces. A design fault found there
is fixed and recorded here before the formal runs.

## Limits to state
Two capacities and two deleted fractions only; three replicates; untrimmed condition only; the live fraction and total
fill are not held constant; written after the earlier results were known.
